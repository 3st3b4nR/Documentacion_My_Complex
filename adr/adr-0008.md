# definir el lenguaje y framework para el backend

## Contexto y planteamiento del problema

Tras definir que MyComplex utilizará un Monolito Modular con Arquitectura Hexagonal, es imperativo seleccionar un stack tecnológico y un paradigma de programación que soporten esta estructura de forma nativa. El lenguaje debe proporcionar herramientas robustas para garantizar el encapsulamiento, evitar que se rompan las fronteras entre los módulos con el paso del tiempo y facilitar la inyección de dependencias. ¿Qué lenguaje y framework son los más adecuados para implementar y proteger esta arquitectura?

## Impulsores de decisión

* Contar con soporte nativo y estricto para la Programación Orientada a Objetos (POO).
* Disponer de mecanismos a nivel de código (interfaces, modificadores de acceso) para proteger los puertos y adaptadores de la Arquitectura Hexagonal.
* Prevenir el alto acoplamiento y el deterioro hacia una "bola de barro" (Big Ball of Mud)[cite: 3] mediante herramientas de validación estructural.
* Mantener un equilibrio entre la viabilidad académica (curva de aprendizaje del equipo) y la robustez técnica.
* Alinear la arquitectura del proyecto con los estándares empresariales más demandados para roles de ingeniería de software en la región antioqueña.

## Opciones consideradas

* Java (Spring Boot / Spring Modulith)
* C# (.NET Core)
* TypeScript (Node.js con NestJS)

## Resultado de la decisión

Opción elegida: **Java con el framework Spring Boot**, operando bajo el paradigma de **Programación Orientada a Objetos (POO)**. 

Java ofrece un sistema de tipado estricto y características nativas de encapsulamiento ideales para definir las fronteras de los módulos. Además, el ecosistema de Spring proporciona inyección de dependencias madura y acceso a herramientas avanzadas como *Spring Modulith*, las cuales permiten escribir pruebas automatizadas que verifican y fuerzan el respeto de los límites entre los módulos, garantizando la mantenibilidad a largo plazo. 

Finalmente, esta tecnología es un estándar industrial en empresas de alto perfil, fortaleciendo la proyección profesional del equipo.

### Consecuencias positivas

* El equipo puede utilizar interfaces claras para separar el dominio de la infraestructura (Hexagonal).
* Se reduce el riesgo de acoplamiento accidental gracias a las pruebas de arquitectura automatizadas.
* El proyecto se construye sobre un ecosistema maduro, con abundante documentación para manejar arquitecturas multi-tenant.

### Consecuencias negativas

* Java tiende a ser más verboso en su sintaxis en comparación con lenguajes como TypeScript.
* El consumo de memoria inicial de una aplicación Spring Boot suele ser mayor, lo que podría requerir un servidor de alojamiento ligeramente más robusto en producción.

## Pros y contras de las opciones

### Java (Spring Boot / Spring Modulith)

* Bien, porque la POO y las interfaces de Java modelan perfectamente la Arquitectura Hexagonal.
* Bien, porque cuenta con herramientas nativas para verificar que no se rompa la modularidad.
* Malo, porque requiere mayor configuración inicial (boilerplate) frente a opciones más ligeras.

### C# (.NET Core)

* Bien, porque es extremadamente eficiente y tiene características de encapsulamiento (ej. `internal`) ideales para monolitos modulares.
* Malo, porque el equipo se siente actualmente con mayor dominio y comodidad trabajando sobre el ecosistema de Java.

### TypeScript (Node.js con NestJS)

* Bien, porque permite compartir el mismo lenguaje (JavaScript/TypeScript) entre el frontend y el backend.
* Malo, porque al ser un lenguaje de tipado estructural (y no nominal como Java), el encapsulamiento y las fronteras de los módulos son más fáciles de romper por error durante el desarrollo.
