# seleccionar un gestor de base de datos multi-tenant

* Estado: propuesto
* Decidentes: Jaider Sebastián Lucuara Cortés - John Esteban Roldán Marín
* Fecha: 2026-09-02


## Contexto y planteamiento del problema

El sistema está pensado para ser distribuido a diferentes clientes, ofreciendo la misma instancia de la arquitectura con la información separada.

## Impulsores de decisión <!-- opcional -->

* Necesidad de aislamiento de datos y escalabilidad progresiva al incorporar nuevos conjuntos (Drivers: Escalabilidad, Escenario 04).
* Cumplimiento estricto de transacciones y conservación de datos ante fallos del sistema (Drivers: Confiabilidad, Escenario 01).
* Optimización y viabilidad del costo de operación e infraestructura sin requerir licencias restrictivas (Drivers: Costo, Restricción de Negocio de Presupuesto).
* Requerimiento de respuestas rápidas en consultas concurrentes para residentes y vigilantes (Drivers: Rendimiento, Escenario 12).
* Cumplimiento estricto de controles de seguridad y acceso a la información, apoyando la Ley 1581 (Drivers: Seguridad).

## Opciones consideradas

* PostgreSQL
* MySQL
* Microsoft SQL Server
* Oracle
* MariaDB
* Amazon Aurora
* Google Cloud Spanner
* MongoDB
* Amazon DynamoDB

## Resultado de la decisión

Opción elegida: "PostgreSQL", porque es la base de datos de código abierto que mejor permite el particionamiento nativo multi-tenant (mediante esquemas o RLS), cumple rigurosamente con transacciones ACID (para la confiabilidad de los datos) y respeta las restricciones de presupuesto al carecer de costos de licencia. 

*Nota de validación:* Para validar definitivamente esta arquitectura se debe construir una **PoC (Proof of Concept)** y no un Spike. Un Spike se usa para investigar tecnologías desconocidas, pero aquí ya conocemos cómo funciona un motor relacional. Una PoC es el mecanismo idóneo porque nos permitirá medir bajo estrés real si la estrategia de aislamiento (RLS/esquemas) rinde según los tiempos esperados y aísla correctamente la información de las unidades residenciales.

### Consecuencias positivas <!-- opcional -->

* Mejora la satisfacción del atributo de confiabilidad asegurando integridad ante cortes o fallos.
* Control total del presupuesto al utilizar software Open Source, permitiendo destinar los recursos a infraestructura en la nube.
* Cumple las restricciones legales (Ley 1581) facilitando la separación por tenant en el núcleo de la base de datos.

### Consecuencias negativas <!-- opcional -->

* Comprometerá la simplicidad inicial, ya que el diseño del modelo multi-tenant exige alta rigurosidad técnica para no mezclar datos accidentalmente.
* Se requieren decisiones de seguimiento sobre la estrategia de backups por cada tenant individual o global.

## Pros y contras de las opciones <!-- opcional -->

### MYSQL

Sistema de gestión de bases de datos relacional de código abierto.

* Bien, porque ofrece un cumplimiento estricto de transacciones ACID
* Bien, porque ofrece soporte nativo para rollback
* Malo, porque su soporte nativo para particionar y aislar la información de distintos clientes en una misma tabla (Row-Level Security) es menos maduro o inexistente sin desarrollo adicional.

### PostgreSQL

Sistema de gestión de bases de datos relacional y orientado a objetos de código abierto.

* Bien, porque ofrece Row-Level Security (RLS) y esquemas, lo que facilita enormemente el modelo multi-tenant.
* Bien, porque respeta las restricciones de presupuesto operativo.
* Malo, porque su curva de aprendizaje para afinar el rendimiento (tuning) en operaciones de alta carga es más pronunciada.

### Microsoft SQL Server / Oracle

Bases de datos comerciales empresariales.

* Bien, porque ofrecen soporte robusto, rendimiento garantizado y características de seguridad avanzadas out-of-the-box.
* Bien, porque su integración en entornos corporativos es muy madura.
* Malo, porque su costo de licenciamiento rompe agresivamente la restricción de presupuesto del proyecto.

### MongoDB / Amazon DynamoDB

Bases de datos NoSQL y/o documentales.

* Bien, porque ofrecen excelente escalabilidad horizontal nativa.
* Bien, porque manejan esquemas flexibles que se adaptan a cambios rápidos.
* Malo, porque comprometen el atributo de confiabilidad transaccional ACID necesario para procesos exactos como estados de reservas y autorizaciones.

### Amazon Aurora / Google Cloud Spanner

Sistemas de bases de datos relacionales distribuidas nativas de la nube.

* Bien, porque delegan la administración, la escalabilidad masiva y la alta disponibilidad.
* Bien, porque resuelven problemas de carga masiva de manera transparente.
* Malo, porque generan un fuerte vendor lock-in y sus costos recurrentes pueden ser impredecibles para la etapa de crecimiento.

### MariaDB

Bifurcación (fork) de código abierto de MySQL.

* Bien, porque mejora el rendimiento de ciertas consultas frente a MySQL estándar.
* Bien, porque mantiene compatibilidad y es totalmente gratuita.
* Malo, porque arrastra las mismas limitaciones que MySQL respecto al modelo multi-tenant a nivel de filas.
