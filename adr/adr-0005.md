# controlar la concurrencia en operaciones criticas

* Estado: propuesto
* Fecha: 2026-09-08

## Contexto y planteamiento del problema

MyComplex puede recibir solicitudes simultáneas sobre un mismo recurso o información, especialmente en operaciones críticas como la creación y modificación de reservas de zonas comunes. Se debe evitar que estas operaciones generen condiciones de carrera, reservas incompatibles, modificaciones perdidas o información inconsistente. ¿Qué mecanismo de control de concurrencia permite garantizar la integridad de las operaciones críticas manteniendo una complejidad y un rendimiento adecuados para MyComplex?

## Impulsores de decisión

* Garantizar la integridad y consistencia de la información.
* Evitar condiciones de carrera en operaciones simultáneas.
* Prevenir reservas duplicadas o incompatibles sobre un mismo recurso.
* Evitar la pérdida silenciosa de modificaciones realizadas por otros usuarios.
* Mantener un rendimiento adecuado cuando varios usuarios utilicen simultáneamente el sistema.
* Reducir bloqueos prolongados sobre los recursos de la base de datos.
* Utilizar mecanismos que puedan implementarse y validarse independientemente de una tecnología de backend específica.
* Permitir comprobar la solución mediante una PoC o Spike.
* Evitar una complejidad innecesaria para el tamaño y alcance actual de MyComplex.

## Opciones consideradas

* **Control optimista mediante versión del registro (Optimistic Locking).**
* **Control pesimista mediante transacciones y bloqueo explícito de recursos (Pessimistic Locking).**
* **Transacciones atómicas complementadas con restricciones de integridad en la base de datos.**

## Resultado de la decisión

Opción elegida: **"Control optimista mediante versión del registro para detectar modificaciones concurrentes, complementado con transacciones atómicas y restricciones de integridad para operaciones críticas"**, porque permite utilizar mecanismos adecuados para los diferentes tipos de conflictos de concurrencia presentes en MyComplex.

El control optimista mediante una versión del registro permitirá detectar situaciones en las que dos usuarios intenten modificar simultáneamente la misma información. Antes de confirmar una modificación, el sistema deberá comprobar que la versión del registro utilizada por el usuario continúa siendo válida. Si la información fue modificada previamente por otra operación, el sistema deberá detectar el conflicto y evitar que una modificación sobrescriba silenciosamente a la otra.

Para operaciones críticas como la creación de reservas de zonas comunes, el control de versiones por sí solo puede no ser suficiente, debido a que dos solicitudes simultáneas pueden intentar crear nuevos registros incompatibles. Por esta razón, estas operaciones deberán ejecutarse mediante transacciones atómicas y complementarse con restricciones de integridad que impidan que el sistema confirme estados inválidos.

La implementación concreta de estos mecanismos dependerá de las tecnologías de backend y base de datos que sean seleccionadas para MyComplex. La alternativa deberá validarse mediante una PoC/Spike utilizando escenarios de solicitudes simultáneas sobre un mismo recurso.

### Consecuencias positivas

* Reduce el riesgo de perder modificaciones realizadas simultáneamente por diferentes usuarios.
* Permite detectar conflictos de concurrencia mediante el control de versiones.
* Evita mantener bloqueos prolongados como estrategia general para todas las operaciones.
* Protege operaciones críticas mediante transacciones atómicas.
* Permite complementar las reglas de negocio con restricciones de integridad en la base de datos.
* Reduce la posibilidad de confirmar reservas incompatibles o estados inconsistentes.
* Permite utilizar diferentes mecanismos según el tipo de operación y riesgo asociado.
* La decisión puede validarse mediante pruebas de concurrencia en una PoC/Spike.

### Consecuencias negativas

* Será necesario implementar mecanismos diferentes según el tipo de operación crítica.
* Los conflictos detectados mediante control optimista deberán ser manejados correctamente por la aplicación.
* Algunos usuarios podrían tener que actualizar la información o repetir una operación cuando ocurra un conflicto.
* Las transacciones y restricciones deberán diseñarse correctamente para evitar afectar innecesariamente el rendimiento.
* Será necesario realizar pruebas específicas con múltiples solicitudes simultáneas.
* La implementación concreta dependerá parcialmente de las capacidades de la tecnología de backend y de la base de datos seleccionadas.

## Pros y contras de las opciones

### Control optimista mediante versión del registro (Optimistic Locking)

Consiste en almacenar una versión o identificador de concurrencia asociado a un registro. Cuando un usuario intenta modificarlo, el sistema comprueba que la versión utilizada continúa siendo la misma antes de confirmar la actualización.

* Bien, porque permite detectar modificaciones realizadas simultáneamente sobre un mismo registro.
* Bien, porque evita sobrescribir silenciosamente los cambios realizados por otro usuario.
* Bien, porque no requiere mantener bloqueos prolongados mientras el usuario consulta o modifica la información.
* Bien, porque ofrece un buen rendimiento cuando los conflictos de concurrencia no son frecuentes.
* Bien, porque puede validarse mediante una PoC utilizando múltiples actualizaciones simultáneas sobre el mismo registro.
* Malo, porque requiere implementar y manejar correctamente los conflictos detectados.
* Malo, porque un usuario puede tener que actualizar la información y repetir la operación.
* Malo, porque por sí solo no garantiza reglas de negocio relacionadas con la creación simultánea de registros incompatibles.

Para MyComplex, esta alternativa resulta adecuada para operaciones en las que varios usuarios puedan modificar simultáneamente un mismo registro, pero requiere complementarse para proteger determinadas operaciones críticas como las reservas.

### Control pesimista mediante transacciones y bloqueo explícito de recursos (Pessimistic Locking)

Consiste en iniciar una transacción y bloquear explícitamente el recurso o registro mientras se realiza una operación crítica, evitando que otras operaciones incompatibles lo modifiquen hasta que la transacción termine.

* Bien, porque evita que varias operaciones modifiquen simultáneamente un mismo recurso protegido.
* Bien, porque puede ser adecuado cuando los conflictos sobre un mismo recurso son frecuentes o tienen consecuencias críticas.
* Bien, porque permite garantizar un acceso exclusivo temporal durante determinadas operaciones.
* Bien, porque puede validarse mediante una PoC ejecutando solicitudes simultáneas sobre un mismo recurso.
* Malo, porque puede generar esperas para otros usuarios.
* Malo, porque puede afectar el rendimiento cuando existen múltiples solicitudes sobre los mismos recursos.
* Malo, porque aumenta el riesgo de bloqueos prolongados o interbloqueos si las transacciones no se diseñan correctamente.
* Malo, porque puede resultar excesivo para operaciones donde los conflictos son poco frecuentes.

Para MyComplex, esta alternativa puede ser útil en casos específicos de alta contención, pero utilizarla como mecanismo general podría introducir bloqueos y complejidad innecesarios.

### Transacciones atómicas complementadas con restricciones de integridad en la base de datos

Consiste en ejecutar una operación crítica como una unidad atómica y utilizar restricciones de integridad en la base de datos para impedir que se confirmen estados que violen las reglas establecidas.

* Bien, porque protege la integridad de la información incluso cuando existen solicitudes simultáneas.
* Bien, porque permite que determinadas reglas críticas sean garantizadas directamente por la base de datos.
* Bien, porque resulta especialmente útil cuando varias solicitudes intentan crear registros incompatibles.
* Bien, porque puede utilizarse para evitar que una operación quede parcialmente completada.
* Bien, porque puede validarse mediante una PoC enviando múltiples solicitudes simultáneas para crear operaciones incompatibles.
* Malo, porque requiere diseñar cuidadosamente las transacciones y restricciones.
* Malo, porque algunas reglas complejas de negocio pueden requerir mecanismos adicionales según la base de datos seleccionada.
* Malo, porque una implementación incorrecta puede afectar el rendimiento o no impedir determinados conflictos.

Para MyComplex, esta alternativa resulta especialmente importante para operaciones críticas como las reservas, donde una simple validación desde la aplicación no es suficiente para garantizar la integridad frente a solicitudes simultáneas.
