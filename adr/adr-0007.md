# implementarautorizacion y control de acceso

## Contexto y planteamiento del problema

Una vez que el usuario ha sido autenticado por el proveedor externo (ADR 06), MyComplex debe determinar qué acciones tiene permitidas. El sistema cuenta con roles específicos (administrador, residente, vigilante, propietario, trabajador) y opera bajo un modelo donde un usuario de un conjunto residencial no debe acceder a la información de otro conjunto. ¿Dónde y cómo debe MyComplex gestionar estas reglas de acceso?

## Impulsores de decisión

* Aplicar permisos estrictos de acuerdo con el rol de cada usuario.
* Garantizar el aislamiento absoluto de la información entre conjuntos residenciales (Multi-Tenancy).
* Mantener la lógica de negocio y las reglas de acceso centralizadas bajo el control del equipo de desarrollo.
* Evitar latencia innecesaria al momento de verificar los permisos.

## Opciones consideradas

* Autorización delegada completamente al proveedor de identidad externo.
* Autorización gestionada nativamente en el backend mediante lectura de tokens y middlewares.
* Autorización externalizada mediante un motor de políticas independiente.

## Resultado de la decisión

Opción elegida: **Autorización gestionada nativamente en el backend mediante lectura de tokens**, porque las reglas que definen qué puede hacer cada perfil están íntimamente ligadas a la lógica de negocio de MyComplex. Intentar modelar estas reglas inmobiliarias dentro de un proveedor externo resulta complejo y difícil de mantener.

El flujo será el siguiente: el backend recibirá el token emitido por el proveedor de identidad. Este token contendrá el rol del usuario y el identificador de su conjunto residencial (`TenantId`). El backend interceptará las peticiones, leerá esta información y ejecutará las validaciones correspondientes antes de permitir el acceso a los datos.

### Consecuencias positivas

* Máximo control sobre las reglas de negocio; los permisos residen en el código fuente de MyComplex.
* Validación de permisos rápida y eficiente, sin depender de consultas externas a otros servidores.
* Se aprovechan los mecanismos de seguridad y filtrado nativos del framework que se elija para el backend.

### Consecuencias negativas

* Requiere sincronizar la configuración del proveedor de identidad para asegurar que envíe correctamente el rol y el `TenantId` dentro del token.
* Exige rigor por parte de los desarrolladores para proteger cada ruta del sistema con los filtros correspondientes.

## Pros y contras de las opciones

### Autorización delegada completamente al proveedor de identidad externo

* Bien, porque centraliza toda la seguridad (quién es y qué hace) en un solo lugar.
* Malo, porque obliga a replicar la estructura del negocio (conjuntos, unidades, roles) en la base de datos de un tercero.
* Malo, porque el backend dependería de llamadas constantes a internet para saber si un usuario tiene permiso.

### Autorización gestionada nativamente en el backend mediante lectura de tokens

* Bien, porque mantiene la autorización acoplada a las necesidades del negocio y desacoplada del proveedor externo.
* Bien, porque garantiza una evaluación de permisos casi instantánea.
* Malo, porque requiere configurar con precisión la lectura y validación del token dentro del código del servidor.

### Autorización externalizada mediante un motor de políticas independiente

* Bien, porque separa las políticas de autorización del código fuente.
* Malo, porque es una solución sobredimensionada que añade una complejidad innecesaria para las necesidades actuales del proyecto.
