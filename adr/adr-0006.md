# utilizar framework nativo de identidad para autenticación y autorización

* Estado: propuesto
* Fecha: 2026-09-08

## Contexto y planteamiento del problema

MyComplex maneja diferentes perfiles de usuario estrictamente diferenciados (administrador, residente, vigilante, propietario y trabajador), pertenecientes a múltiples conjuntos residenciales. El sistema debe proteger las cuentas y cumplir con la Ley 1581 de 2012, previniendo el acceso cruzado entre copropiedades. ¿Qué tecnología o estrategia de autenticación y autorización proporciona el equilibrio adecuado entre seguridad, aislamiento multi-tenant y esfuerzo de desarrollo para MyComplex?

## Impulsores de decisión

* Garantizar un alto nivel de seguridad en la gestión de credenciales, tokens y sesiones.
* Proteger el sistema contra vulnerabilidades críticas como *Broken Access Control* (OWASP Top 1).
* Diferenciar claramente entre autenticación (quién es) y autorización (qué puede hacer y sobre qué conjunto).
* Garantizar el aislamiento estricto inyectando la pertenencia al conjunto residencial (`TenantId`) en el mecanismo de autorización.
* Mantener un equilibrio adecuado entre esfuerzo de desarrollo, seguridad, infraestructura y costos.

## Opciones consideradas

* Implementación propia de autenticación y autorización desde cero.
* Uso de módulos o frameworks nativos del ecosistema tecnológico del backend (ej. ASP.NET Core Identity).
* Proveedor o servicio externo de gestión de identidad (ej. Auth0, Keycloak).

## Resultado de la decisión

Opción elegida: **"Uso de módulos o frameworks nativos del ecosistema tecnológico del backend"**, porque permite a MyComplex aprovechar componentes probados de seguridad sin asumir los altos riesgos de programar criptografía manual ni los costos económicos recurrentes de plataformas de terceros. 

Esta solución permite inyectar nativamente los *claims* de Rol y `TenantId` dentro de los tokens JWT emitidos. El backend utilizará estos *claims* en sus políticas de autorización para rechazar cualquier petición donde el usuario intente acceder a datos de un conjunto residencial que no le corresponde, garantizando el aislamiento multi-tenant. La configuración exacta de estas políticas y la emisión del token deberá validarse previamente mediante una PoC o Spike técnica.

### Consecuencias positivas

* Se reduce drásticamente el riesgo de vulnerabilidades asociadas a la gestión manual de contraseñas y sesiones.
* Se facilita la implementación estructurada de roles, permisos y políticas de autorización por conjunto residencial.
* Se aprovechan los mecanismos estandarizados de seguridad del ecosistema elegido sin incurrir en licencias externas.
* Se garantiza el aislamiento de datos al centralizar la validación del `TenantId` en los filtros de autorización.

### Consecuencias negativas

* El equipo de desarrollo deberá familiarizarse profundamente con la configuración de las políticas de autorización, validación de *claims* y personalización del módulo de identidad del framework.
* Se debe realizar una PoC para comprobar que el aislamiento por *claims* funciona correctamente antes del desarrollo completo.

## Pros y contras de las opciones

### Implementación propia de autenticación y autorización desde cero

Consiste en programar internamente la lógica de algoritmos de hashing, validación de contraseñas, generación de JWT y middleware de permisos.

* Bien, porque otorga un control absoluto y directo sobre cada línea de código desarrollada.
* Malo, porque introduce un riesgo de seguridad crítico debido a la alta probabilidad de cometer errores humanos en criptografía.
* Malo, porque incrementa innecesariamente el esfuerzo de mantenimiento y el riesgo de vulnerabilidades.

Para MyComplex, esta opción es descartada por el alto peligro de introducir vulnerabilidades graves que comprometan los datos de la copropiedad.

### Uso de módulos o frameworks nativos del ecosistema tecnológico del backend

Consiste en utilizar los mecanismos integrados (como ASP.NET Core Identity) para la generación segura de tokens, validación de credenciales y autorización basada en políticas (*Policy-based authorization*).

* Bien, porque ofrece una solución madura, probada y resistente frente a ataques comunes de inyección o secuestro de sesión.
* Bien, porque permite inyectar fácilmente datos del contexto (como el `TenantId`) directamente en el token del usuario.
* Bien, porque reduce el esfuerzo de desarrollo y no genera costos adicionales de infraestructura.
* Malo, porque impone una curva de aprendizaje para entender la configuración avanzada de seguridad del framework.

Para MyComplex, esta es la opción más conveniente porque garantiza altos estándares de seguridad industrial adaptados a un esquema multi-tenant de bajo costo.

### Proveedor o servicio externo de gestión de identidad

Consiste en delegar la autenticación a un proveedor Identity-as-a-Service o desplegar un servidor independiente (ej. Auth0 o Keycloak).

* Bien, porque externaliza la infraestructura de identidad y ofrece características avanzadas (como inicio de sesión social o MFA) listas para usar.
* Malo, porque introduce dependencia de latencia y disponibilidad hacia servicios externos.
* Malo, porque genera costos económicos recurrentes por usuario activo (en el caso de SaaS) o alta complejidad de infraestructura (en el caso de Keycloak).

Para MyComplex, esta opción resulta sobredimensionada para la etapa actual y contradice las restricciones presupuestales del proyecto.
